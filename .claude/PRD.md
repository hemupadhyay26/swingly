# PRD: Swingly

Status: Draft v1 — for internal reference (Claude Code working memory for this project)
Last updated: 2026-09-26

## 1. One-line summary

> Give us a character + description → generate its hanging artwork and expressions → turn it into an interactive character that can live and react on any website. "Character" here is broad — it can be an anthropomorphic mascot, or just as easily a symbolic/cultural object (e.g. a protective charm or token), so the pipeline shouldn't hard-assume a face or limbs.

## 2. Problem / Motivation

Websites feel static. A small, character-driven mascot that hangs off the corner of a page, swings like a pendulum, and reacts to the visitor adds personality and delight with very little integration cost for a frontend developer — but today there's no easy way to (a) generate character art suited for this specific use case, or (b) drop it into a site with working physics/animation/interaction out of the box.

Swingly aims to solve both halves: an **AI asset generator** and a **reusable interactive runtime**, packaged so a developer can go from "I want *this* character hanging in the corner of my site" to a working widget with minimal effort.

## 3. Goals

1. Given a character name + text description, generate:
   - A **main hanging artwork** of the character, attached to a long web/rope/thread/similar tether, with a clearly defined **anchor/hang point** suitable for pendulum-style physics.
   - A **3×3 sprite sheet** (9 cells) of the same character showing 9 discrete expressions/poses.
2. Package the generated assets into a **reusable NPM package** that:
   - Renders the character hanging from a configurable corner/edge of the viewport.
   - Simulates natural **pendulum/swing motion** (idle sway, drag-and-release, momentum/damping).
   - Reacts to user interaction (hover, click/tap, drag) by switching expressions/poses.
   - Exposes a simple API for a frontend developer to configure and control the character (which expression to show, trigger animations, hook into events).
3. Be **character-agnostic** — the same generation pipeline and runtime must work for any character, mascot, or custom description, without any single character being special-cased in the design (see [Section 10](#10-example-use-case-reference-implementation) for the reference example used to validate this). This includes non-anthropomorphic subjects, such as a symbolic/cultural protective charm or token (e.g. a *nimbu-mirchi* lemon-and-chili charm, a *nazar*/evil-eye charm, or similar from any tradition) — the design shouldn't hard-assume a face, limbs, or literal poses; a non-anthropomorphic subject can express its mood through cues native to its form instead (glow, sparkle, motion, shape change, etc.).

### 3.1 Version 1 (MVP) definition

Before building out the full vision above, v1 is deliberately scoped down to answer one core feasibility question: **can a pre-generated image asset set be dropped into an NPM package and produce a working hanging/reacting character with almost no integration code?**

The v1 flow is:

1. Produce a character's asset set — `main.png` (hanging pose) + the expression files (3×3 sheet or individual images). For v1 these can be generated by whatever means is fastest (manual generation, one-off AI image gen) — the point is to have a real asset set to build against, not to have the automated text→assets pipeline finished yet.
2. Build the **NPM package** so it is **asset-driven**: it takes the generated images (and a manifest describing them) directly as input/config — it does not require any per-character custom code, only pointing the package at the asset files.
3. The bar for success is **integration simplicity**: a developer who already has a running website should be able to add the character by pasting a couple of lines of setup code (import + init with the asset paths) — no build step changes, no custom rendering code, no manual coordinate math.
4. Automating the *generation* side (text description → assets, prompt design, the full AI pipeline in Section 6.1) is treated as the next phase once the package itself is proven to work well with a hand-produced asset set. **The npm package is the v1 priority; the generation pipeline follows once the package's asset contract is validated.**

## 4. Non-goals (for v1)

- Full-body skeletal rigging / bone-based animation. v1 targets sprite-based (image swap) animation, not skeletal deformation.
- 3D characters — this is a 2D system.
- Voice, sound effects, or chat/AI-driven conversation from the character (may be a future extension, not required now).
- Multi-character scenes / characters interacting with each other — not in scope.
- Mobile native (iOS/Android) SDKs — v1 is web-only (NPM package for JS/TS frontends).

## 5. Users & primary use case

- **Primary user of the generator**: someone (developer, designer, indie hacker) who wants a custom mascot and provides a character name + description.
- **Primary user of the NPM package**: a frontend developer who has (or generates) a character asset set and wants to embed the interactive mascot in their site (React/Vue/vanilla JS) with minimal setup.

## 6. System overview — two major components

### 6.1 Asset Generation Pipeline

**Input:** character name + free-text description (e.g. name, visual style, color palette, personality/pose cues).

**Output (per character):**
1. `main.png` (or similar) — the character hanging from a long web/rope/thread/similar element, transparent background, composed so that:
   - There is an identifiable, consistent **anchor point** (e.g. top of the thread) that maps to a fixed pixel/percentage coordinate in the image, used later to attach the pendulum pivot.
   - The character's body hangs naturally below that anchor, in a "hanging/dangling" default pose.
2. `expressions.png` — **deferred, not currently produced by the automated pipeline** (see [Section 7, item 2](#7-open-questions--decisions-needed) for why). Intended design, kept here for when it's revisited: a **3×3 grid sprite sheet**, 9 equally-sized cells, each cell = one expression/pose of the same character, same art style/proportions/framing as the main artwork so swaps look seamless. The 9 expressions:
   1. Hi / Hello
   2. Happy
   3. Love
   4. Surprise
   5. Cool
   6. Confused
   7. Sleepy
   8. Charming
   9. Waving
3. `manifest.json` — metadata describing the generated set: character name/description, image dimensions, anchor point coordinates, sprite sheet grid layout (rows/cols/cell size), and a name→cell-index mapping for the 9 expressions.

**Key requirements:**
- Consistent art style, proportions, and canvas framing between `main.png` and each `expressions.png` cell so runtime swaps don't visibly "jump."
- Transparent backgrounds on all generated assets.
- Deterministic, machine-readable output (the manifest) so the runtime package never has to guess coordinates or cell order.
- Character-agnostic prompt construction — the pipeline takes the user's character + description and augments it internally with the "hanging pose" / "expression sheet" / "consistent style" constraints needed for good generation results.

### 6.2 Interactive Runtime (NPM package)

**Input:** the generated asset set (`main.png`, `expressions.png`, `manifest.json`) plus developer configuration (which corner/edge, thread length, physics tuning, etc).

**Core capabilities:**
- **Hanging placement** — attach the character to a configurable corner or side of the viewport (e.g. top-right, top-left) via a rendered thread/rope from a fixed page anchor down to the character's anchor point.
- **Pendulum physics** — natural idle swing (subtle, continuous), plus interactive swing: dragging the character and releasing it should swing with momentum and damping like a real pendulum on a string.
- **Expression/reaction system** — swap to a given expression cell from the sprite sheet in response to interaction events (hover → "Hi", click → random reaction, idle timeout → "Sleepy", etc.) with configurable triggers, and an imperative API to set expression manually.
- **Animation/behavior hooks** — support simple built-in behaviors (e.g. periodic wave, look-at-cursor tilt) and expose events/callbacks so a developer can extend behavior.
- **Simple integration API** — something like:
  ```js
  import { HangingCharacter } from "swingly";

  const char = new HangingCharacter({
    assets: "/characters/my-character/manifest.json",
    corner: "top-right",
    threadLength: 180,
  });
  char.mount(document.body);
  char.on("click", () => char.setExpression("surprise"));
  ```
- Framework-agnostic core, with thin wrappers/examples for React and vanilla JS (Vue as stretch goal).

## 7. Open questions / decisions needed

These are unresolved and should be revisited with the user before/while building:

1. **Image generation backend** — which model/tool actually produces `main.png` / `expressions.png`? (This session has access to Highsfield image-generation MCP tools — need to confirm that's the intended generator, or if there's another preferred pipeline/API.)
2. ~~Consistency across the 9 expression cells and the main pose~~ — **attempted and deferred**: tried both a single-call 3×3 grid (`images.generate()`) and an `images.edit()` call using the real `main.png` bytes as the reference image, with increasingly explicit prompting (matching fill-ratio, thread length, "do not zoom in"). Neither reliably held scale — the model consistently "zoomed in" to fill each grid cell, shrinking the thread/enlarging the character relative to the main pose, so runtime swaps visibly jumped. The 9-separate-calls-plus-manual-compositing option (generate each expression at `main.png`'s own full 1024×1024 size, then downscale/paste into the grid ourselves in code) was identified as the likely real fix, since it makes the scale-down a deterministic code operation instead of a model decision — but it's ~9x the generation cost per character and hasn't been built. For now, expression-sheet generation is **removed from the automated pipeline** (`skills/page-swingly` only outputs `main.png` + `manifest.json`); `HangingCharacter` already treats `expressions` as optional, so characters just hang/swing with no face-swapping until this is revisited.
3. **Anchor point detection** — is the anchor point specified by the generation prompt/convention (e.g. always top-center of canvas) or does the pipeline need to detect it post-generation (e.g. via image analysis)?
4. **Rendering approach for the rope/thread** — pre-rendered as part of the generated image vs. drawn dynamically by the runtime (SVG/canvas line) so its length can be configured/animated. (Dynamic thread is likely better for the "configurable thread length + pendulum" requirement — main character art may need to exclude the thread and just expose the anchor point instead.)
5. **Physics engine choice** for the NPM package — hand-rolled simple pendulum math vs. a library (e.g. Matter.js) — affects bundle size vs. development speed.
6. **Priority/sequencing** — build order between the generation pipeline and the NPM package (can be developed somewhat in parallel using placeholder/mock assets for the package).
7. ~~Where `skills/spiderman-example` fits~~ — superseded: Spider-Man was dropped as the reference character (see [Section 10](#10-example-use-case-reference-implementation)) before that skill was ever built. `skills/page-swingly` is the actual generator, validated end-to-end against several other reference characters instead.

## 8. Success criteria

**V1 (MVP) bar — must hit this first:**
- Given a hand-produced asset set (`main.png` + expression files) for the reference character, a developer can `npm install` the package, point it at those assets, and get a working hanging + expression-swapping character on an already-running page by pasting only a couple of lines of setup code — no custom rendering code, no manual coordinate math.
- Swapping between the 9 expressions looks visually seamless (consistent style/scale/position). **Not met for the automated pipeline** — see [Section 7, item 2](#7-open-questions--decisions-needed); the package itself supports expression-swapping fine (it's optional per-character), but the generator currently can't produce a matching sheet, so no shipped character has one.

**Later / full-vision bar:**
- A developer can supply a character name + description and get back a usable asset set (main art + expression sheet + manifest) without manual image editing.
- The pendulum swing feels physically plausible (damped oscillation, momentum on drag-release) rather than robotic/linear.
- The same pipeline and package work for at least two visually distinct test characters (the reference example plus one other) to validate character-agnosticism.

## 9. High-level phases (proposed)

1. **Spec & scaffolding** (this doc + repo/skill structure) — current phase.
2. **Produce a real asset set** — `main.png` + expression files for the reference character (Section 10), by whatever means is fastest for now (manual/one-off generation), just to have real inputs to build the package against.
3. **NPM package MVP** — asset-driven package that consumes that asset set directly (hanging placement + expression swapping at minimum) and can be dropped into an existing page with a couple of lines of setup code. This is the key v1 feasibility milestone (see [Section 3.1](#31-version-1-mvp-definition)).
4. **Physics & interaction polish** — pendulum swing (idle + drag-release momentum/damping) and reaction triggers, layered onto the working MVP.
5. **Asset generation pipeline** — automate the text description → assets flow (prompt design, generation calls, manifest emission) against the package's now-proven asset contract.
6. **Integration pass** — generate a new character end-to-end through the automated pipeline and drive it through the package; fix any consistency/anchor issues found.
7. **Packaging & docs** — publishable NPM package, README/integration guide, framework examples.

## 10. Example Use Case (Reference Implementation)

Everything above (Sections 1–9) is written generically on purpose — the design must not special-case any one character. **Spider-Man** was the originally planned proof-of-concept character but was dropped early: the OpenAI Images API's safety system rejects recognizable copyrighted/trademarked characters outright (`moderation_blocked`), and no amount of prompt rewording is an appropriate way around that. `skills/spiderman-example` referenced below was never actually built as a result.

The real reference characters, generated end-to-end through the working pipeline, live in `characters/` — a mix of non-anthropomorphic charms (`nimbu-mirchi`, a lemon-and-chili protective charm; `evil-eye-horseshoe`; `nazar-battu`) and animal mascots (`panda`, `webster` the spider), validating character-agnosticism across both categories called out in Section 3.

- **Hang point:** every character shares the same convention — anchored near the top of the frame via a thread/rope/web, normalized anchor point `(0.5, 0.05)` in the manifest.
- **Expression mapping:** not currently applicable — expression-sheet generation is deferred (see [Section 7, item 2](#7-open-questions--decisions-needed)), so shipped characters are main-pose-only.
- **Where it lives:** the generator is [skills/page-swingly](../skills/page-swingly); the NPM package + demo site (which renders these characters live) is [swingly](../swingly).
- **Purpose:** prove out the asset contract (anchor point, manifest) and the runtime behavior (hang, swing, react, drag) on real characters before generalizing further. These are test cases for the design, not special cases within it.
